# Issue 12: manual PM handoff

The existing Project Manager definition fulfills the specification's Product Manager role for manual discovery; no role is renamed or activated. Assign a task to PM in the workflow, open Manual PM handoffs, prepare a deterministic draft, review it for sensitive data and copy it yourself into the subscription UI. The server has no subscription integration or provider invocation.

Preparing a handoff freezes task metadata and adds a pending project approval gate. Revision zero is a system placeholder, explicitly not a human artifact, and cannot be approved. Submission creates an immutable human-attributed revision and a new pending approval superseding the placeholder or rejected revision. Use the existing CEO review semantics. Rejected revisions remain stored and cannot be bypassed through generic approval resubmission. Approval never changes task status; existing dependencies and explicit simulation transitions still apply. Archived projects reject writes. Submitted content is bounded to 20,000 characters, treated as untrusted text and escaped by React. Strict handoff command schemas reject client-supplied provenance. Audit records reference the submission ID and SHA-256 digest rather than duplicating the submitted body. The append-only application-role grants protect artifact rows; database owners can change history and a compromised app can fabricate inserts as documented in prior ADRs.

Run migrations and reapply scripts/app-privileges.sql with the migration owner. The runtime role receives SELECT/INSERT on handoff/artifact records and UPDATE only on the handoff version. Preserve all prior security limitations: login availability, trusted ingress, manual database credential/grant deployment, client-side pagination and audit provenance. This first handoff screen loads all records and needs pagination before large datasets. Review sensitive metadata before copying: no claim of automatic redaction or verified external AI output is made. No network adapter interface is introduced in this change.

## PR 13 review decisions

PM artifact decisions use `handoff.review` with the artifact ID, approval version and explicit acknowledgement of human provenance; the generic `approval.decide` command rejects all PM approvals. Review must target the latest non-placeholder revision with a pending, unsuperseded approval. The UI exposes its human provenance and escaped content before the review form. Server-side authorization cannot prove a human read the screen; it enforces the identity, revision and pending-state boundary.

Approval gating remains **project-wide**, matching Phase 2 and Phase 3A policy: a PM handoff on task A blocks task B in that project, even without a dependency edge. This conservative governance gate is separate from task dependency completion. Changing to task-scoped approval would alter established policy and needs a separate design decision. Regression tests show unrelated work is blocked until the current artifact is approved.

Task title, owner, priority and criteria cannot change after a handoff exists. Task status/version may advance without changing the snapshotted metadata. To request a revised brief, create a new PM task with revised criteria; an in-place brief revision workflow is not implemented. Rejected responses may still be resubmitted against the immutable brief. Tests protect the freeze and reject duplicate brief creation.

First submission marks the system placeholder `superseded`, rather than CEO-rejected, and records a distinct `SYSTEM` audit event in the same transaction. Human rejection remains `rejected`, preserving reason and timestamp. The pending replacement continues to gate the project. Historical placeholder rows labeled rejected by older code are retained unchanged as historical evidence.
