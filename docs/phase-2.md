# Phase 2 simulation

The CEO-only workflow records projects, assignments, dependencies, simulated transitions and approvals in PostgreSQL. It does not run employees, invoke providers, modify GitHub, deploy or execute code. No sample projects are seeded. Project archive preserves history. `/api/workflow` requires the existing CEO session, a matching Origin and a validated JSON command. Version checks and project-level transaction locks reject stale decisions and serialize graph changes. Dependencies can change only while the dependent task is draft. In-progress and done transitions require completed dependencies and approved current approval requests.

A CEO may resubmit a rejected request with a revised action. The new pending request links to the original; the original decision and reason remain unchanged. A superseded rejection no longer blocks, but its replacement blocks until approved. Only one replacement per rejection is allowed; each subsequent rejection can be resubmitted in turn. Audit records label the CEO actor and simulation mode.

The workflow screen paginates projects, tasks, approvals and recent activity in stable timestamp/ID order with empty and save states. Data is currently loaded in full before client-side pagination to preserve dependency and supersession context; this is unsuitable for large datasets and needs server-side cursor pagination before production.

## Database privileges and audit integrity

Use a migration-owner credential for migrations and seed, and a distinct non-owner, non-superuser runtime login. Set `DATABASE_MIGRATION_URL` to the migration-owner connection for `npm run db:migrate`; `DATABASE_URL` is the runtime connection. The fallback to `DATABASE_URL` exists for disposable local/CI databases only. Apply `scripts/app-privileges.sql` as the migration owner after every migration (for example `psql "$DATABASE_MIGRATION_URL" -v ON_ERROR_STOP=1 -f scripts/app-privileges.sql`). It creates the NOLOGIN group role `aicompany_app`, revokes public schema access, and grants the app role only SELECT and INSERT on audit events; UPDATE, DELETE, TRUNCATE and schema creation are not granted. An administrator must create a distinct login, grant it membership in `aicompany_app`, and ensure it has no ownership, elevated role memberships or direct/public grants that bypass this boundary. Store both URLs securely, never in the repository. The script is not a substitute for verifying effective grants on the actual host. The migration owner and database administrators can alter audit history; protect those credentials and use independent audit retention. A compromised app can insert fabricated events, so this is append-only protection, not cryptographic provenance.

Run migrations, apply grants, then seed using the migration-owner connection (`DATABASE_URL="$DATABASE_MIGRATION_URL" npm run db:seed`). Integration tests use a disposable owner database to test role restrictions. Run `npm run test:integration` and `npm run test:e2e` with test credentials as described in the README. Existing Phase 1 security limitations remain; see [security review](security-review.md). Do not use production or customer data for tests.
