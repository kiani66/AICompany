# ADR: simulation runtime boundary

Status: foundation for review; no activation is authorized. All six agent rows remain execution-disabled under the existing database constraint. The CEO session and origin checks protect the runtime API; no agent can authorize a run. The policy denies real execution, non-CEO actions, enabled agents, missing run approval, disabled budgets, unmet dependencies, the kill switch and any tool capability. The only adapter is deterministic local code: it receives no prompt and performs no network, filesystem, code or GitHub operations. Fake token estimates and micro-USD values are accounting units, not provider usage or real charges.

The kill switch defaults on and absent budgets deny requests. The CEO explicitly creates a request, approves it, reserves and queues it, starts it and completes the fake simulation; nothing schedules or triggers automatically. The request stage records an awaiting-approval proposal only; it cannot execute. Policy is checked at request, queue, start and completion. Phase 2 project approval gates remain in force. The runtime takes a global transaction advisory lock, then the same project lock as workflow mutations, serializing kill-switch changes, budget updates and reservations. Three scope rows (global, project, agent) must exist and have sufficient remaining token and micro-USD capacity. Reconciliation releases the estimate and records deterministic fake usage; cancellation or fake failure releases it. The fake provider consumes one simulated token and zero micro-USD. Output beyond the reservation is rejected and the transaction rolls back. Idempotency keys identify request payloads; replay with the same payload returns the original run and different payloads conflict. Version checks reject stale commands.

## Boundaries and remaining work

The unused `REQUESTED` and `BLOCKED` states were removed: a proposal starts at `AWAITING_APPROVAL`, while a denied operation leaves the run and budget unchanged and records a separate denial. Migration rejects any pre-existing rows with the removed states rather than silently changing them. Fake failure is a deliberate deterministic test outcome, not error recovery for a real provider. Synchronous transitions have no background worker, replay scheduler or lease. Success evidence is copied to the append-only ledger as well as the updateable run row. The role grants protect the ledger from updates and deletes by the configured runtime role, but a compromised app can insert fabricated entries and database owners can change history. Validated, authenticated CEO commands denied by runtime policy or state checks roll back to a savepoint; the outer transaction commits a sanitized denial bucket and one append-only audit event per operation/reason/minute. Concurrent identical denials increment the bucket atomically. The record contains CEO actor, operation, categorical reason, policy version, fixed simulation context, minute and last-seen timestamps, and count; it excludes request keys, prompts and submitted content. A finite operation and reason vocabulary bounds new rows per minute, but retention must be managed by a privileged operator. Invalid JSON, unauthenticated requests, origin failures, unexpected infrastructure failures and an uninitialized company are not recorded as policy denials. If denial storage fails the whole transaction fails closed and no durability is claimed. A future activation design needs independent evidence storage, denial retention, key rotation, recovery and a security review before use. The app can fabricate audit inserts; existing Phase 1 session/availability risks and Phase 2 privilege deployment and client-side pagination limits remain. Production readiness is not claimed.

Apply migrations with `npm run db:migrate`, then reapply `scripts/app-privileges.sql` using the migration-owner credential as described in `docs/phase-2.md`. No runtime settings, budgets, projects, tasks or runs are seeded. Set simulation budgets and the switch only through CEO controls in an isolated environment; no paid service is required. Budget limits are lifetime totals, not billing periods. The dashboard shows the latest 100 runs, denial buckets and ledger records, not a complete paginated history.

The separate non-owner database login must inherit only `aicompany_app` and not own the tables or have elevated/direct privileges. The grant script gives it SELECT/INSERT and UPDATE only on count and last-seen columns of denial aggregates; the accompanying audit event remains append-only. A compromised application can alter aggregate counts or insert fabricated evidence, and database owners can alter all records. Integration tests use a distinct temporary login to check that UPDATE, DELETE and TRUNCATE on the ledger fail, but deployment must independently verify effective grants and credentials.
